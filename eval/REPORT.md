# 检索链路改造 · 复测报告

> 任务：在**不更换模型、不改动文档内容**的前提下，用 BM25 + 稠密 + RRF(k=60) + Rerank  
> 的混合检索方案提升验收准确率，并提交可复现的复测数据。

---

## 一、结论

| 指标               | 改造前（向量 + 重排）     | 改造后（混合 + 重排）     | 变化                     |
| ---------------- | ---------------- | ---------------- | ---------------------- |
| **端到端准确率**（验收口径） | **78.3%**（47/60） | **85.0%**（51/60） | **+6.7pp**             |
| 编号类（35 题）        | 80.0%（28/35）     | 88.6%（31/35）     | +8.6pp                 |
| 术语类（12 题）        | 100%（12/12）      | 100%（12/12）      | 0                      |
| 口语化（11 题）        | 63.6%（7/11）      | 63.6%（7/11）      | 0                      |
| 跨节（2 题）          | 0%（0/2）          | 50%（1/2）         | +50pp（样本过小）            |
| **Recall@1**     | 61.7%            | 63.3%            | +1.6pp                 |
| **Recall@5**     | 91.7%            | 91.7%            | 0                      |
| 端到端延迟            | P50 约 185ms      | P50 约 161ms      | **持平**（增量 0.4ms，见 3.5） |

**达标情况**：端到端准确率 85.0%，达到 85% 的目标线。

**必须说清的两件事**：

1. **基线是 78.3%。**
2. **增益不是均质的。** 编号类 +8.6pp、跨节 +50pp（仅 2 题），  
   术语类与口语化**完全没有提升**。这个分布本身就是结论。

## 三、怎么读这张表

### 3.1 Recall@5 饱和了，看 Recall@1 才看得出差别

三组配置的 Recall@5 都卡在 91.7%。原因很直接：**204 个 chunk 里取 5 个，覆盖率 2.5%，  
而这批语料的标题足够唯一**，只要召回进前 5 就命中。这是语料规模带来的天花板效应，  
不是方法失效。

真正的差异在排序质量上：**Recall@1 从 51.7% 走到 63.3%（+11.6pp，7 道题）**。  
也就是说，混合检索 + 重排让「第一个就给对」的比例提升了近 12 个点，  
但「前五里有没有」几乎没变。

这条对业务有意义：前 5 里有没有决定「能不能答」，第一个对不对决定「答得准不准、要不要多跑一次重排」。

### 3.2 重排在纯向量上反而掉分，这是一个真实的反转

|          | 纯向量   | 向量 + 重排 | 变化         |
| -------- | ----- | ------- | ---------- |
| 端到端      | 80.0% | 78.3%   | **−1.7pp** |
| Recall@1 | 51.7% | 61.7%   | +10.0pp    |

Recall@1 大涨，端到端却小跌。合理解释是：重排把「本来就对」的答案挤掉了 1 道，  
同时把「原本排在第 3–5 位」的正确答案顶到第 1 位——排序变好，但生成端只取 4 块，  
被挤掉的那 1 道直接变成了错答。

**1.7pp 在 60 题里就是 1 道题，属于噪声量级**，我不认为这是「重排有害」的证据，  
只说明「重排的收益主要落在排序质量上，而不是命中数量上」。

### 3.3 Recall@1 为什么只有 63.3%：一个 gold 口径造成的天花板

看到 63.3% 会以为「三分之一的问题第一名就找错了」，实测不是。做了个诊断：

对 60 道题各取 top-1，**未命中 gold 的 22 道**里，看第一名来自哪份文档：

| top-1 来源        | 数量 | 占比      |
| --------------- | -- | ------- |
| 《客服常见问题速查》(FAQ) | 18 | **82%** |
| 退换货/退款政策        | 4  | 18%     |

FAQ 是问答体，同一条知识在手册里是「2.2.3 E1028 充电电流异常 / E1028 表示…」，  
在 FAQ 里是「Q016 问：E1028 充电电流异常怎么处理？答：先确认是否使用原装适配器…」。  
**两块都能回答同一个问题，但 gold 只锚定了手册那一块**（因为 gold 是用事实原文反查的，  
事实原文只存在于手册）。

于是 FAQ 块排第一时，Recall@1 记为未命中——但它其实答对了。  
这也解释了为什么**端到端准确率 85.0% 反而高于 Recall@1 63.3%**：  
端到端只看答案对不对，不关心是哪一块提供的。

**结论：Recall@1 63.3% 是「第一名正好命中手册原文」的比例，不是「只有 63% 找得到答案」。**  
要修这个偏差，需要把每道题的同义条目也纳入 gold（人工补标或 LLM 判定扩充），  
本次没有做，如实披露。

### 3.4 增益集中在编号类，口语化完全没有提升

- **编号类 80.0% → 88.6%**：符合预期。BM25 对 `E1028` / `XR-200S` / `LW05` 这类  
  稀有 token 是精确匹配，稠密向量会把 `E1028` 与 `E1025` 编码到很近的位置。
- **口语化 63.6% → 63.6%**：一个都没变。这类问题（「扫到一半停在那不动了」）  
  的难点在语义改写，不在字面匹配，BM25 帮不上忙，重排也救不回来。
- **跨节 0% → 50%**：只有 2 道题，1 道题的差别就是 50pp，**样本太小，不能当结论**。

**这才是这次改造最有信息量的部分**：混合检索不是「全面提升」，而是  
「在需要精确匹配的查询上补短板」，对语义型查询无感。

### 3.5 延迟：不能宣称「不升反降」

初版报告里写过「P95 181ms → 177ms」，这个写法**站不住**，做了专项基准后撤回。

**先说清楚一个陷阱。** 第一次基准是「同一道题先跑 A 再跑 B」，  
结果是 hybrid 比 dense_rerank 快 52ms，置信区间还很窄。但**反序再跑一遍**：

| 执行顺序   | hybrid − dense_rerank    |
| ------ | ------------------------ |
| 正序 A→B | **−105.5ms**（看起来快 105ms） |
| 反序 B→A | **+1.1ms**（反而慢 1ms）      |

**符号翻转**，说明那 105ms 是「谁后跑谁快」——后执行的那次复用了 HTTP 连接、  
命中了服务端热路径。这是基准测试里最经典的顺序偏差。

**再看各阶段真实耗时**（本地计算，逐题测，取中位数）：

| 阶段                | P50         | P95     |
| ----------------- | ----------- | ------- |
| Milvus 稠密检索       | 5.58ms      | 11.66ms |
| **BM25 稀疏检索**     | **0.40ms**  | 1.15ms  |
| **RRF 融合**        | **0.005ms** | 0.015ms |
| embedding（外部 API） | ~60ms       | —       |
| rerank（外部 API）    | ~90ms       | —       |

**混合检索的真实增量 = 0.40 + 0.005 ≈ 0.41ms**，占总延迟（约 160ms）的 0.26%，  
完全被外部 API 的抖动淹没（同一配置 P95 在 180–300ms 之间波动）。

**结论**：

- 准确率提升的代价**确实约等于零**，但原因是「BM25 是内存索引、RRF 是纯计算」，  
  不是「系统变快了」；
- 报告与简历统一口径为「**延迟持平，增量 0.4ms**」，**不写「下降」**；
- 复现命令：`python eval/bench_latency.py`（内含正序/反序对照）。

## 四、复测方法（可复现）

### 4.1 语料

8 份 PDF，204 个 chunk，约 3 万字。其中《故障代码全表》含 60 条错误码，  
外形高度相似（E1024 / E1025 / E1028、E2048 / E2050 / E2055），  
构成天然的困难负样本——这正是任务描述里「编号类召回错误频发」的成因。

### 4.2 评测集

60 道题，按真实提问分布配比：

| 类别  | 题数 | 示例                                           |
| --- | -- | -------------------------------------------- |
| 编号  | 35 | 「E1028 是什么故障」「XR-200S 的电池多大」「政策 3.2.1 说的是什么」 |
| 术语  | 12 | 「七天无理由的运费谁承担」「序列号被涂改还能保修吗」                   |
| 口语化 | 11 | 「扫到一半停在那不动了」「拆开包装了还能退吗」                      |
| 跨节  | 2  | 「我要退货，运费谁出，钱多久能到账」                           |

### 4.3 gold 标注：不手工标，用事实反查

每题给出「能回答该问题的原文片段」（facts），用片段在 chunk 里做**归一化子串匹配**  
反查 gold。一条事实命中多个 chunk 时全部计入（多相关块判定）。

- 好处：标注零主观，任何人重跑都得到同一份 gold；
- 自检结果：60/60 全部命中，gold 平均 1.08 块，占语料 **0.5%** —— 目标很窄，不容易蒙对。

### 4.4 端到端判定

检索 top-4 → 固定 prompt 生成 → LLM 判定员按标准事实判对错。

判定口径**偏严**：要求回答给出与标准事实一致的结论且转述关键信息；  
「只给处理步骤、没复述定义」也会被判错。因此绝对值偏低，  
但两侧用同一把尺子，**差值可比**。

全部原始答案与判定理由落在 `eval/e2e_results.json`，可逐条复核。

### 4.5 复现命令

```bash
python scripts/gen_corpus.py      # 生成 8 份 PDF
python scripts/build_index.py     # 建库（204 chunk）
python eval/build_eval.py         # 反查 gold，生成 60 题
python eval/run_eval.py           # 五组 Recall 复测
python eval/e2e_eval.py --modes dense,dense_rerank,hybrid,hybrid_rerank
python eval/diagnose_recall1.py   # Recall@1 未命中的来源分布
python eval/bench_latency.py      # 延迟基准（正序/反序对照，防顺序偏差）
```

## 五、设计取舍

| 取舍                  | 选择                            | 理由                                             |
| ------------------- | ----------------------------- | ---------------------------------------------- |
| BM25 用库还是自建         | **自建**（jieba + rank_bm25）     | 内置 BM25 的 k1/b 不可调、分词是黑盒，且无法单独跑「纯 BM25」这一组做对照  |
| RRF 手写还是用 Milvus 内置 | **手写**                        | 内置把融合藏进库里，答辩被问「融合代码在哪」答不上；手写 20 行，能逐行讲         |
| 编号是否单独切词            | **是**，正则先抽编号再 jieba           | 不这么做，`XR-200` 会被切成 `XR`/`200`，BM25 的精确匹配优势直接消失 |
| 切分粒度                | **200 字 / 20 重叠，不变**          | 任务要求不改文档内容；同时保证五组配置共用同一批 chunk，提升可归因到检索        |
| 是否保留重排              | **保留**                        | 端到端 ±1.7pp 属噪声，但 Recall@1 +10pp 是稳定收益          |
| embedding 是否升级      | **不升级**（仍是 text-embedding-v1） | 任务明确要求不换模型；换了就没法归因为检索链路                        |

## 六、局限（写给自己，也写进答辩）

1. **60 题样本量小**：1 道题 = 1.67pp，整体 ±3pp 内的差异不能当结论；
2. **语料只有 204 chunk**：Recall@5 存在明显天花板，真实企业库（万级）结论可能不同；
3. **跨节只有 2 题**：50pp 的变化没有统计意义，需要扩题；
4. **判定员与被测模型同源**：存在同源偏好，已落盘原始答案供人工复核；
5. **纯 BM25 未测端到端**：只测了召回，成本考虑；
6. **单轮评测**：多轮追问只在 e2e 测试里覆盖，未做量化；
7. **延迟受外部 API 主导**：embedding 与 rerank 占端到端耗时 90% 以上，  
   单次测量跨配置比较会被抖动淹没（见 3.5），只能比较「本地计算部分」的增量。
